# Дизайн · Умный ввод/поиск (SmartQueryInput) — Voice + Search

> Дата: 2026-06-29 · Статус: утверждён к имплементации
> Контекст: голосовой ввод на `/report` «плохо проработан»; нужен такой же умный ввод
> на `/monitor` как поиск по активным алярмам.

## 1. Цель и проблема

**Проблема (по фидбеку, все 4 пункта):**
1. Нет обратной связи — не видно, что распозналось; нельзя поправить текст до отправки.
2. Непонятно, что спрашивать — нет подсказок/примеров.
3. Слабый разбор (NLU) — demo-`mockNlu` примитивен.
4. Нет текстовой альтернативы — акцент только на микрофоне.

**Цель:** единый переиспользуемый примитив ввода (текст + голос + живой транскрипт +
подсказки), применённый на двух экранах с разными обработчиками запроса.

## 2. Архитектура

Один presentation-примитив `SmartQueryInput`, два потребителя с разной семантикой запроса:

```
SmartQueryInput (presentation, без бизнес-логики)
 ├─ текстовое поле (печать — первичный ввод, всегда доступна)
 ├─ VoiceButton (существует) + живой транскрипт, редактируемый перед отправкой
 ├─ чипы-подсказки (кликабельные примеры запросов)
 └─ emit: onChange(text) [каждое изменение] / onSubmit(text) [Enter/кнопка]
        │
        ├─ /report  → onSubmit → voice.queryReport(text) → отчёт (NL→бэкенд)
        └─ /monitor → onChange → локальный фильтр alarmSearch(q, visible) (без бэкенда)
```

**Почему примитив, а не два компонента:** UX-часть (поле + микрофон + транскрипт +
подсказки) идентична — дублирование запрещено. Расходится только «что делать с запросом»:
report = NL→бэкенд-отчёт; monitor = мгновенный локальный фильтр списка. Потребитель
передаёт свой обработчик.

**Отвергнутые альтернативы:**
- Два независимых компонента → дублирование voice-UX, рассинхрон при правках.
- Всё через бэкенд-NLU (и на monitor) → лишняя задержка для простого фильтра списка.

## 3. Компоненты

### 3.1 `SmartQueryInput` (новый) · `web/src/components/ui/SmartQueryInput.tsx`

```ts
interface SmartQueryInputProps {
  value: string
  onChange: (text: string) => void          // каждое изменение (live-фильтр)
  onSubmit?: (text: string) => void          // Enter / кнопка «Построить»
  placeholder?: string
  suggestions?: string[]                      // чипы-примеры: клик → onChange + onSubmit
  voice?: boolean                             // показать VoiceButton (report=true)
  voiceState?: 'idle' | 'recording' | 'processing'
  onRecorded?: (blob: Blob) => void
  busy?: boolean                              // спиннер во время обработки запроса
  className?: string
}
```
- Текстовое поле — первичный ввод; микрофон — опциональный аддон (закрывает п.4).
- Живой транскрипт попадает в `value` и редактируется до `onSubmit` (закрывает п.1).
- Подсказки — ряд кликабельных чипов под полем (закрывает п.2).
- a11y: `role="search"`, `aria-live="polite"` на статус распознавания, фокус-ринги.
- Чистая презентация: НЕ ходит в сеть, НЕ парсит — только эмитит.

### 3.2 `alarmSearch` (новый) · `web/src/state/alarmSearch.ts`

```ts
function alarmSearch(query: string, list: IncidentSummary[]): IncidentSummary[]
```
- Пустой/пробельный query → возвращает list без изменений.
- Матч (регистронезависимо) по: `vehicle_plate`, `driver`, `alarm_label_ru`, `source`.
- Синонимы риска: «критичные/критично» → `severity==='critical'`; «риск>N»/«риск > N»
  → `risk_score > N` (парсинг числа до ~3 знаков).
- Чистая детерминированная функция (без побочных эффектов) — легко тестируется.

## 4. Состояния и обработка ошибок
- SmartQueryInput: idle / recording / processing / busy; нет разрешения на микрофон →
  поле остаётся рабочим (печать), ошибка не валит экран.
- Monitor search: пустой результат → empty-state + быстрый сброс; live-фильтр не сбрасывает
  выбранную карточку, если она остаётся в выборке.
- Report: ошибка запроса — существующий `ErrorBlock` + retry (без изменений).
