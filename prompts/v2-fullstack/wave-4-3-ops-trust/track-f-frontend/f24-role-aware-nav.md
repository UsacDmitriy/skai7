# f24 · Роль-зависимая навигация: NAV согласован с ролью (issue #4)

> Трек **Frontend** (оболочка/NAV) · **Волна 4.3 (Ops & Trust)** · целостность экранов. Против `00-CONTRACT.md`
> §6 («Монитор: Логист — только телематика»), §7.8 (AC «Монитор: Логист — без DMS-алармов»;
> «Карта по ролям: переключатель роли скрывает/показывает **слои**»), §7.6 (роль-токены/иконки).
> **Модель:** 🔵 Sonnet — селектор + вёрстка NAV, без алгоритмов; гейт = секция Check.
> **Владеет:** правкой `web/src/App.tsx` (NAV) + малым селектором `navForRole(role)` в state-слое роли.
> Зависит от `f13` (`state/role.ts` — единый источник роли) и `w3-18` (группа «AI» в NAV).

## Цель

issue #4: NAV в `App.tsx` показывает **одно и то же меню всем ролям**, тогда как роль (`RoleProvider`,
`state/role.ts`) фильтрует только **данные внутри экранов** (Логист не видит DMS-алармы — `roleFilter.ts`).
Рассогласования «пункт меню ведёт на пустой/нерелевантный для роли экран» сейчас нет, но механизма
скрытия секций под роль тоже нет — добавляем его так, чтобы NAV **оставался согласован** с in-screen
фильтрацией: ни один работающий для роли экран не прячем, ни один запрещённый роли — не показываем.

## Состав (роль→секции, с §-обоснованием)

**Канонические роли** (источник — `state/role.ts` / `components/map/types.ts`): `logist` 🏭 / `dispatcher` 🛡
/ `security` 🔒. Переиспользуем **этот же** источник истины — второй роль-модели не заводим.

Разбор контракта по секциям NAV:

| Секция NAV | logist | dispatcher | security | §-обоснование |
|---|---|---|---|---|
| Мониторинг (Карта, Безопасность) | ✅ | ✅ | ✅ | §6/§7.8: Логист **пользуется** монитором (телематика, online/offline) — фильтруется контент, не доступ к экрану. Скрывать нельзя. |
| Видеоаналитика (События, Заявки, …) | ✅ | ✅ | ✅ | §7.8: лента событий — ролевой switcher; у Логиста она **не пустая** (`filterByRole` оставляет не-DMS). Прятать = противоречить in-screen фильтру. |
| Дашборды и отчёты | ✅ | ✅ | ✅ | Контракт не привязывает отчёты к роли (§7.8 «Отчёт» — без роль-ограничений). Не over-hide. |
| Парк (Здоровье парка, Навигация/РЭБ) | ✅ | ✅ | ✅ | Контракт молчит о роль-ограничении парка. Не over-hide. |
| AI (Копилот, Метрики) | ✅ | ✅ | ✅ | §8 не привязывает AI-слой к роли. **Единственный кандидат на роль-специфичность** — см. «Допущение». По умолчанию видно всем. |

**Вывод (важно для проверяющего):** контракт мандатит фильтрацию роли на уровне **данных/слоёв**, а не
на уровне разделов меню. Единственное явное роль-ограничение — «Логист — без DMS» (§6/§7.8) — уже
реализовано как контент-фильтр и **не означает** недоступности секции (Логист штатно работает в монитор/
ленте с отфильтрованным контентом). Поэтому **жёстких hide по ролям контракт не требует** — реализуем
**минимальный согласованный механизм**, а не фактические скрытия.

## Что сделать

1. **Механизм** (без форка роль-модели): в state-слое роли добавить чистый селектор
   `navForRole(role: Role, groups: NavGroup[]): NavGroup[]` + опциональное поле `roles?: Role[]` у `NavItem`
   (и/или `NavGroup`). Семантика: `roles` отсутствует ⇒ пункт виден **всем** ролям (текущее поведение —
   дефолт безопасен); задан ⇒ виден только перечисленным. Селектор отбрасывает пустые группы.
2. **`Sidebar`** рендерит `navForRole(role, NAV)` (роль из `useRole()`), а не сырой `NAV`. Точка истины —
   `RoleProvider` (f13); второго стора/контекста не создавать.
3. **Маппинг по умолчанию — без скрытий:** ни одному `NavItem` не проставляем `roles` (контракт молчит,
   см. таблицу). Механизм заведён и используется — но фактическая видимость идентична текущей для всех ролей.
   Так issue #4 закрыт инфраструктурно (NAV теперь умеет роль-фильтрацию, согласованную с контентом),
   без догадок и без over-hide.
4. **Если проверяющий подтвердит** роль-специфичность (см. «Допущение»), единственная безопасная правка —
   проставить `roles: ['dispatcher','security']` на группе «AI» (W4-кандидат). Менять это в одном месте,
   контент-фильтрам (`roleFilter.ts`) правок не нужно.

> Не дублировать `Role`/значения — импортировать из `state/role.ts`. Не трогать `roleFilter.ts`, страницы,
> роуты: меняется только видимость пунктов NAV, маршруты доступны по прямому URL (deep-link не ломаем).

## Check

- **Перед началом:** `grep -n "export type Role" web/src/state/role.ts && grep -n "useRole" web/src/state/role.ts`
  — источник f13 на месте (есть в `integration`). Grep пуст → **СТОП**, дефект треку: роль-модель не форкать.
- Переключение роли в `RoleToggle` (лента/монитор) **не убирает** ни одной работающей секции у Логиста —
  Мониторинг/Видеоаналитика/Отчёты/Парк видны (согласованность с `filterByRole`: контент фильтруется, доступ — нет).
- `navForRole` — чистая функция (без `Date.now()`/мутаций входа), покрыта юнит-тестом: `roles` нет ⇒ виден
  всем; задан ⇒ только перечисленным; пустые группы отброшены; неизвестная роль не роняет (дефолт-видимость).
- Sidebar читает роль из `useRole()` (единый `RoleProvider`), второго роль-источника в коде нет (grep).
- Прямой переход по URL на скрытый-для-роли путь (если такой появится) не падает (NAV ≠ guard роутинга — только меню).
- a11y NAV сохранён (`aria-current`, hover-раскрытие 48→240). `npm run typecheck` зелёный.
- **Документированное допущение (контракт молчит про NAV-уровень):** §6/§7.8/§8 не задают скрытие **разделов**
  по роли — только фильтрацию данных/слоёв. Поэтому дефолт = «видно всем», скрытий нет. Если продукт-роль-модель
  всё же требует прятать секции (напр. «AI» только для Диспетчера/Безопасника) — проверяющий подтверждает,
  и правка сводится к одному `roles: [...]` на группе/пункте. **Логическая корректность > догадки.**
