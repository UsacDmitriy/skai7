## W5-1 · Очередь верификации событий (event review queue) · ✅ → Волна 5.1 (§11, b30/f26/tu-review, x10)

- **Обоснование:** Lytx review-queue (паттерн лидера); Фомин — «39 ДТП в телематике, видео подтвердило 5»:
  нужен workflow подтверждения/отклонения событий с видео-доказательством, а не разовая кнопка verify.
- **Датасеты:** ДОСТАТОЧНО. Персист статусов — `output/` (паттерн `actions.csv`); KPI очереди уже готовятся:
  `avg_time_to_triage` (b25), `evidence_rate` (§10, Волна 4.4).
- **Контракт:** §11 (аддендум): `ReviewItem {incident_id, status: pending|validated|dismissed, reviewer_note}`,
  `GET/POST /api/review-queue`; AC: фильтр «непросмотренные», счётчик в NAV.
- **Эскиз промптов:** `b30` (queue service + journal) → `f26` (экран очереди `/review`; снимает f22-редирект
  `/quick-report`? нет — это отдельный маршрут) → `tu-review`.
- **Риски:** конфликт со статусной моделью `actions.csv` (verify уже пишет туда) — нужен единый статусный
  словарь; иначе два источника истины.

## W5-2 · Коучинг-цикл водителя (closed loop) · ✅ → Волна 5.2 (§12, b31-генератор/b32-сервис/f27/tu-coaching, x11)

- **Обоснование:** Оздоев (Газпромнефть, дословно): инцидент → авто-уведомление водителя → обучающий
  материал → тест (18/20) → уведомление руководителя → эскалация при повторном нарушении за 30 дней.
  Паттерн Samsara coaching effectiveness / Lytx coaching workflow. Самая монетизируемая фича бэклога.
- **Датасеты:** **GAP** — нужен синтетический `training_assignments` (incident_id, driver_id, course_id,
  assigned_at, test_score, passed, repeat_within_30d), генерация детерминированно от существующих алармов.
- **Контракт:** §12: `CoachingAssignment`, `GET /api/coaching/{driver_id}`, KPI `repeat_violation_rate`.
- **Эскиз:** датасет-промпт (генератор) → `b31` (coaching service) → `f27` (вкладка в DriverReport) → `tu-coaching`.
- **Риски:** без реальных данных обучения фича демонстрационная — честно пометить «синтетика» в UI
  (паттерн §8.0); не обещать HR-интеграцию в MVP.

## W5-3 · Green-zone / позитивный скоринг водителя · ✅ → Волна 5.3 (§13.1, b33, фича #25)

- **Обоснование:** Netradyne DriverStar/GreenZone (анализ 100% времени, признание хорошего вождения);
  Оздоев трекает «зелёную зону» как KPI.
- **Датасеты:** ЧАСТИЧНО — track_points покрывают только окна событий (не 100% времени вождения);
  пересечение video-флота с sensors/fuel — 2 ТС. Честный вариант: «дни без событий» + соблюдение
  скоростного режима в имеющихся треках (аналог честности §8.0).
- **Контракт:** §13: `PositiveScore {plate, clean_days, smooth_ratio}`; интеграция в DriverReport.
- **Эскиз:** `b32` (агрегация) → правка f7/f16 (блок «позитив») → `tu-positive`.
- **Риски:** статистическая хлипкость на 2 днях данных — обязателен дисклеймер периода.

## W5-4 · Единый скоринг водителя + геймификация · ◐ ЧАСТИЧНО → Волна 5.3 (§13.2, b34/f28: скоринг + лидерборд, фича #26); геймификация (баллы/команды/призы/чат-бот) ОСТАЁТСЯ — нужен мобильный канал водителя

  (баллы/команды/призы/чат-бот-коуч).
- **Датасеты:** скоринг — достаточно (risk_score + события обоих источников уже блендятся);
  геймификация — нужен журнал начислений (синтетика, паттерн W5-2).
- **Контракт:** §14: `DriverScore` (единый, видео+телематика, веса зафиксировать) + лидерборд.
- **Эскиз:** `b33` (унификация скоринга поверх §2) → `f28` (лидерборд) → `tu-score`.
- **Риски:** двойной счёт с risk_score §2 — единый скоринг должен ИМПОРТИРОВАТЬ §2, не дублировать
  (урок b27); геймификация без mobile-канала водителя — макет.
