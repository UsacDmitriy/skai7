## Цель

Довести view `v_incidents` (спайн всего API) до Definition of Done на уже построенном файле: гарантировать
**ровно 54 строки**, детерминизм подзапросов, null-безопасность и отсутствие коллизий имён таблиц —
без изменения набора колонок из §1.3.

## Состав (правки в `api/sql/10_v_incidents.sql`)

- **Анти-размножение строк:** каждый `LEFT JOIN` (`tp`/`dms`/`front`/`ts`) обязан давать **≤1 строку на `alarm_id`**
  (агрегаты `MIN`/`ROW_NUMBER()=1`), иначе count > 54. Зафиксировать `count(*)=54` как инвариант.
- **Коллизия имён:** трек берём строго из `video_events__track_points`, **не** из `navigation__track_points`
  (одноимённый суффикс существует после b1) — указать полное имя таблицы.
- **Детерминизм первой точки `tp`:** `ROW_NUMBER() OVER (PARTITION BY "alarm_id" ORDER BY "point_index")=1`
  с устойчивым tie-break (вторичный `ORDER BY` по стабильному ключу), чтобы `lat/lon` не «прыгали» между прогонами.
- **Детерминизм `dms`/`front`:** `MIN("media_relative_path")` по каналу 5/1 — стабильный выбор кадра.
- **Null-safety:** `video_available` = `CASE WHEN "VideoCount" > 0 THEN 1 ELSE 0` (никогда NULL);
  `lat/lon`/`cam_*_url`/`mileage_km` могут быть NULL по данным, но колонка присутствует всегда.
- **Типы:** `CAST(a."Speed" AS DOUBLE)`, числовые поля приведены — без строковых артефактов из CSV.

## Check

- `SELECT count(*) FROM "v_incidents"` = **54** (инвариант не нарушен ни одним JOIN).
- Двойной прогон `make db` → идентичные `lat/lon`/`cam_*_url` (детерминизм подзапросов).
- Существуют обе таблицы `video_events__track_points` и `navigation__track_points`; view берёт первую.
- `video_available ∈ {0,1}` без NULL; для DMS-алярмов с видео `cam_dms_url` непуст.
- Колонок ровно как в §1.3 (enrichment-поля по-прежнему НЕ в view — их даёт b5/b2).
- Регрессий по smoke x3 (спайн ETL→view) нет.
